# 控制器框架规范 v4（mindrealm 中台）

> **适用系统**：mindrealm——一套面向实验室自动化 / 设备集成的 HTTP 中台  
> **文件类型**：工程规范文档（面向设备集成开发者、代码审查者）  
> **领域**：软件工程 / 硬件驱动抽象

---

## 系统四层架构

```
HTTP 请求 (/api/operate, /api/order)
        │
        ▼
┌──────────────────┐
│  router/device.py │   动态加载 service 模块，参数校验，状态机
└────────┬──────────┘
         ▼
┌──────────────────────────┐
│  service/operate/*.py    │   业务动作（"连上这台设备"、"锁资源"）
│  service/order/*.py      │   业务技能（"移动到 P1"、"吸液 100μL"）
└────────┬─────────────────┘
         ▼
┌──────────────────────────┐
│  controllers/<family>/   │   设备驱动：把"物理动作"变成 Python 方法
└────────┬─────────────────┘
         ▼
    真实硬件 / 外部 SDK / 远程服务
```

**核心约束**：service 层不允许直接写 socket、import pymodbus、调厂商 DLL——只能拿已连好的控制器对象调方法。

---

## 控制器三大职责

1. **管理物理连接**（建链、断链、重连、心跳）
2. **暴露领域语义方法**（`move_absolute`、`read_holding_registers`，而非 `send_bytes`）
3. **管理实例生命周期**（进程内同一设备只保留一份连接，避免端口抢占）

---

## 强制接口规范（5 组方法）

| 组别 | 必须方法 | 说明 |
|------|---------|------|
| **连接** | `connect()` / `disconnect()` / `reconnect()` / `is_connected` | `is_connected` 可属性或方法 |
| **状态** | `get_status()` / `get_error_info()` / `clear_errors()` | `get_status()` 返回 dict，至少含 `connected` 和 `last_error` |
| **控制** | `enable()` / `disable()` / `reset()` / `emergency_stop()` | 不适用设备可省略，须在 README 中说明 |
| **数据** | 领域命名方法（`move_absolute`、`get_liquid`） | 禁止暴露 `send_packet`、`raw_cmd` 等底层细节 |
| **释放** | `close()` | 进程退出 / atexit 时由上层统一调用 |

## 全局池 + 工厂函数（强制三件套）

```python
xxx_manager: Dict[str, XxxController] = {}      # 模块级池

def create_xxx_instance(...) -> XxxController:
    """纯创建，不缓存。连不上也返回对象，标记 is_connected=False。"""

def get_or_create_xxx_instance(..., device_id="xxx") -> XxxController:
    """Service 层唯一入口：池中不存在则由工厂建并缓存。"""

def clear_xxx_instance(device_id):
    """从池移除并 close()。供 /api/operate 的 connect.py 和 atexit 钩子使用。"""
```

**关键约束**：
- 池 key = `device_id`（设备逻辑名），不是 IP / 端口（IP 可变）
- 连接失败工厂**不抛异常**，返回 `is_connected=False` 的半成品实例
- Service 层只能通过 `get_or_create_xxx_instance()` 拿实例，不允许 `XxxController(...)` 直接 new

## 设备类型决策树

```
1. 通讯方式？
   ├─ 以太网 TCP 长连接   → §3.1 长连接 TCP 模板（Dobot 风格）
   ├─ Modbus TCP/RTU     → §3.3 Modbus 模板（多从站复用）
   ├─ 串口自定义协议      → §3.4 串口模板（Pipettor 风格）
   ├─ HTTP / REST        → §3.5 HTTP 模板
   └─ 厂商 Python SDK / DLL → §3.2 SDK 包装模板（Hitbot 风格）

2. 需要长期保活 / 心跳？
   ├─ 是（机械臂、Vision Server、PLC）→ 另起 <device>_connect.py 监控线程
   └─ 否（短命令型：鼠标点击、LIS）→ 不写监控线程

3. 一个物理连接挂多个从站？
   └─ 是（Modbus RS-485 多从站）→ 物理连接池 + VirtualInstanceController 包装器

4. 需持久化参数（点位、配置）？
   └─ 是（机械臂点位）→ 用 utils.params.equ_params 存到 public/params/
```

## 各设备类型核心要点

### TCP 长连接（Dobot 风格）
- 监控线程：周期调 `get_status()` 确认链路；状态写到 `equ_params`；N 次失败触发重连。
- 下发方法必须在 `threading.RLock()` 内执行（防粘包）。
- 解释器退出时检查 `sys.is_finalizing()` 优雅退出 daemon 线程。

### SDK 包装（Hitbot 风格）
- `os.chdir(lib_path)` 仅在 DLL 加载瞬间临时切换，立刻恢复原路径（否则 Flask / APScheduler 相对路径全崩）。
- 厂商 SDK 常非线程安全，调用前加 `self._lock`。

### Modbus 多从站复用
- **物理连接**只缓存一份；多逻辑设备通过 `VirtualInstanceController` 代理，自动注入/替换 `slave_id`。
- 白名单机制：新增方法须同步更新包装器的 `_is_modbus_operation` 和 `_method_accepts_slave_id`。

### 串口自定义协议（Pipettor 风格）
- 三段式调用："下发指令 → 读 ACK → 轮询状态"，不要合并为 blocking 大函数。
- 新写串口控制器须加池（避免 COM 口独占冲突）。

### HTTP 控制器
- 有状态（需保活）：用单例 `__new__` + `_instances` 字典 + `threading.RLock()`。
- 无状态（LIS/LMS 等）：直接封装 URL 前缀 + 认证 + 错误规整即可，不需要池。
