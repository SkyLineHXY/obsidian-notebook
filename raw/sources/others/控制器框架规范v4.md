# 控制器框架规范（Controllers Framework Spec）

本文件面向的读者：

- 第一次拿到一台新设备（机械臂、PLC、串口仪器、HTTP 模块、厂商 SDK……）、准备把它接进 mindrealm 中台的人；
- 想知道"我该新建一个 `controllers/xxx/` 目录，还是复用已有目录"的维护者；
- 想弄清楚"控制器里应该写什么、不应该写什么"的评审人。

它回答一个核心问题：**"一台设备写成控制器"到底要满足哪些约定。**

---

## 0. 为什么需要这层抽象

项目整体分成四层，请先把这张图记下来：

```
HTTP 请求 (/api/operate, /api/order)
        │
        ▼
┌──────────────────┐
│  router/device.py │   —— 动态加载 service 模块，参数校验，状态机
└────────┬──────────┘
         ▼
┌──────────────────────────┐
│  service/operate/*.py    │   —— 业务动作（"连上这台设备"、"锁这个资源"）
│  service/order/*.py      │   —— 业务技能（"移动到 P1"、"吸液 100μL"）
└────────┬─────────────────┘
         ▼
┌──────────────────────────┐
│  controllers/<family>/   │   —— 设备驱动：把"物理动作"变成 Python 方法
└────────┬─────────────────┘
         ▼
    真实硬件 / 外部 SDK / 远程服务
```

**service 层不允许直接写 socket、不允许直接 import pymodbus、不允许直接调厂商 DLL**。它只能拿到一个"已经连好的控制器对象"，然后调方法。所以控制器层的职责是：

1. **管理物理连接**（建链、断链、重连、心跳）；
2. **暴露领域语义的方法**（`move_absolute`、`read_holding_registers`、`get_liquid` 而不是 `send_bytes`）；
3. **管理实例生命周期**（进程内同一设备只保留一份连接，避免端口抢占 / 串口冲突）。

---

## 1. 通用骨架：不管什么设备，控制器都要有这些东西

一个合格的控制器子目录，标准长相如下：

```
controllers/<family>/
├── __init__.py           # 对外导出的符号
├── <device>.py           # 控制器类 + 工厂函数 + 全局池
├── <device>_connect.py   # 连接监控 / 心跳线程（可选）
├── README.md             # 接线、配置项、已知坑（推荐）
└── lib/ or libs/         # 厂商原生 SDK / DLL / so（如有）
```

控制器类本体必须提供以下 **5 组接口**（根据设备能力可以裁剪，但命名必须一致，便于前端与流程引擎统一调用）：

| 组别 | 方法 | 说明 |
| ---- | ---- | ---- |
| **连接** | `connect(params)` / `disconnect()` / `reconnect()` / `is_connected` | `is_connected` 可以是属性或方法，调用方要能一眼判断设备是否在线 |
| **状态** | `get_status()` / `get_error_info()` / `clear_errors()` | `get_status()` 返回 `dict`，至少含 `connected` 和 `last_error` |
| **控制** | `enable()` / `disable()` / `reset()` / `emergency_stop()` | 不适用的设备（例如纯串口仪器）可省略，但要在 README 里说明 |
| **数据** | `read(...)` / `write(...)` 或领域方法（`move_absolute`、`get_liquid`） | **命名用领域语言**，不要暴露 "send_packet"、"raw_cmd" 这种底层细节 |
| **释放** | `close()` | 进程退出 / `atexit` 时由上层统一调用，同时 `disconnect()` |

### 1.1 全局池 + 工厂函数（强制）

**为什么要这么写**：硬件连接是昂贵且独占的资源（TCP 端口、串口句柄、USB 句柄），如果每次 `/api/order` 请求都重新建链，会出现：

- 前一个请求没结束，端口已经被后一个请求占走；
- 重连频繁触发设备本身的看门狗；
- 上层状态（位置、使能状态）丢失。

所以每个控制器文件里都必须有三个对称的函数 + 一个模块级字典：

```python
# 模块级池：{device_id: instance}
xxx_manager = {}

def create_xxx_instance(..., device_id: str = None) -> XxxController:
    """工厂：纯创建，不缓存。内部处理超时/重试，连不上也要返回对象，标记为未连接。"""

def get_or_create_xxx_instance(..., device_id="xxx") -> XxxController:
    """池化入口：service 层只调这个。不存在则通过工厂建并缓存。"""

def clear_xxx_instance(device_id):
    """从池里移除并 close()。供 /api/operate 的 connect.py、atexit 钩子使用。"""
```

### 1.2 强约束

- 池的 key 是 **device_id**（= `device_config.json` 里的 `name`），不是 IP、不是端口；IP/端口可能变，设备逻辑名不能变。
- **service 层只能通过 `get_or_create_xxx_instance(device_id=...)` 拿实例**，不能 `XxxController(...)` 直接 new。
- 连接失败时 **工厂函数不要抛异常**，要返回一个 `is_connected == False` 的半成品实例；由上层调用方根据 `is_connected` 决定是否继续。这样避免请求处理线程在导入期就崩掉。
- 如果设备支持"一个物理连接服务多个逻辑设备"（最典型：一路 RS-485 挂多个从站），池里应该只缓存**物理连接**一份，逻辑设备用包装器绕过去（见 3.3 Modbus 章节）。

## 2. 小白决策树：拿到一台新设备，该套哪个模板

问自己四个问题，顺序回答：

```
1. 这台设备的通讯方式是什么？
   ├─ 以太网 / TCP 长连接             → §3.1 长连接 TCP 模板（Dobot 风格）
   ├─ Modbus（TCP 或 RTU）            → §3.3 Modbus 模板
   ├─ 串口（自定义协议）              → §3.4 串口模板（Pipettor 风格）
   ├─ HTTP / REST                     → §3.5 HTTP 模板（Mouse / LIS SDK 风格）
   └─ 厂商给了 Python SDK / DLL / so  → §3.2 SDK 包装模板（Hitbot 风格）

2. 要不要长期在线、需要心跳？
   ├─ 要（机械臂、Vision 服务器、PLC）   → 另起 <device>_connect.py 写监控线程
   └─ 不要（短命令型：鼠标点击、LIS 建样本）→ 不写监控线程

3. 一个物理连接是否挂多个从站/逻辑设备？
   ├─ 是（Modbus 一路串口 N 个从站）   → 物理连接池 + VirtualInstanceController 包装器
   └─ 否                              → 普通 device_id → 实例池

4. 需不需要持久化参数（点位、配置）？
   ├─ 要（机械臂点位、库位坐标）       → 用 utils.params.equ_params 存到 public/params/
   └─ 不要                            → 只在实例属性里
```

接下来按答案挑模板。

## 3. 按设备类型的细化写法

下面每一类都给出：**适用场景 → 骨架代码 → 注意事项 → 本仓库参考实现**。

### 3.1 长连接 TCP 设备模板

**适用**：机械臂控制口（Dobot 29999 端口）、Vision Master 文本协议、自研 PLC 控制柜……任何**一次建链、多次下发、长期保活**的设备。

#### 文件结构

```
controllers/<family>/
├── <device>.py         # 控制器类 + 工厂/池
└── <device>_connect.py # 状态监控线程
```

#### 控制器本体骨架（`<device>.py`）

```python
import socket, threading, time, sys
from typing import Any, Dict, Optional
from utils.logger import logger

# 默认配置（方便外部不传参也能起来）
DEFAULT_IP = "192.168.1.100"
DEFAULT_PORT = 29999
CONNECT_TIMEOUT = 3
MAX_RETRY = 3

class XxxController:
    def __init__(self) -> None:
        self.is_connected: bool = False
        self._sock: Optional[socket.socket] = None
        self._last_error: Optional[str] = None
        self._factory_config: Optional[Dict[str, Any]] = None
        self._lock = threading.RLock()     # 保护下发，必备

    # ---- 连接 ----
    def _connect_with_retry(self, ip, port, timeout=CONNECT_TIMEOUT, retries=MAX_RETRY):
        """工厂函数调它。每次尝试都 catch 住，全部失败就把 is_connected 置 False。"""
        for i in range(retries):
            try:
                s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
                s.settimeout(timeout)
                s.connect((ip, port))
                self._sock = s
                self.is_connected = True
                return
            except Exception as e:
                self._last_error = str(e)
                logger.warning(f"连接 {ip}:{port} 第 {i+1}/{retries} 次失败: {e}")
                time.sleep(0.5)
        self.is_connected = False

    def close(self):
        """进程退出时由上层 atexit 调。必须做到幂等，可被多次调用。"""
        try:
            if self._sock:
                self._sock.close()
        finally:
            self._sock = None
            self.is_connected = False

    # ---- 领域方法 ----
    def move_absolute(self, x, y, z, r): ...
    def get_point(self): ...
    def emergency_stop(self): ...

# ---- 全局池 + 工厂（强制写法）----
xxx_manager: Dict[str, XxxController] = {}

def create_xxx_instance(ip=None, port=None, auto_connect=True,
                        connect_timeout=None, max_retry_count=None,
                        device_id=None) -> XxxController:
    inst = XxxController()
    if auto_connect:
        inst._connect_with_retry(
            ip or DEFAULT_IP, port or DEFAULT_PORT,
            connect_timeout or CONNECT_TIMEOUT,
            max_retry_count or MAX_RETRY,
        )
    inst._factory_config = dict(ip=ip, port=port, device_id=device_id)
    return inst

def get_or_create_xxx_instance(ip=None, port=None, device_id="xxx", **kw) -> XxxController:
    if xxx_manager.get(device_id) is None:
        xxx_manager[device_id] = create_xxx_instance(
            ip=ip, port=port, device_id=device_id, **kw
        )
    return xxx_manager[device_id]

def clear_xxx_instance(device_id):
    inst = xxx_manager.get(device_id)
    if inst:
        inst.close()
        xxx_manager[device_id] = None
```

#### 监控线程（`<device>_connect.py`）

对**需要保活**的设备必须写。做三件事：

1. 周期性调一次 `get_status()` 或轻量只读命令，确认链路活着；
2. 把状态/位置 `update_path` 写到 `equ_params` 的 `sensor/<device_id>/...`，前端自动能看到；
3. 连续 N 次失败就触发重连或清实例。

骨架：

```python
import threading, time, atexit, sys
from utils.params import equ_params
from utils.logger import logger
import utils.device_config as device_config
from .<device> import get_or_create_xxx_instance, clear_xxx_instance, xxx_manager

_connections = {}         # {device_id: DeviceConnect}
_shutdown_event = threading.Event()

class DeviceConnect:
    def __init__(self, device_id, ip, port):
        self.device_id = device_id
        self._stop = threading.Event()
        self._thread: threading.Thread | None = None
        self._fail_count = 0
        self.MAX_FAILURES = 3
        self.ctrl = get_or_create_xxx_instance(ip=ip, port=port, device_id=device_id)

    def _monitor(self):
        while not self._stop.is_set():
            if hasattr(sys, "is_finalizing") and sys.is_finalizing():
                return
            try:
                # 轻量心跳
                point = self.ctrl.get_point()
                equ_params.update_path(f"sensor/{self.device_id}/point", value=point)
                self._fail_count = 0
            except Exception as e:
                self._fail_count += 1
                logger.warning(f"{self.device_id} 心跳失败 {self._fail_count}/{self.MAX_FAILURES}: {e}")
                if self._fail_count >= self.MAX_FAILURES:
                    logger.error(f"{self.device_id} 连续失败，触发重连")
                    clear_xxx_instance(self.device_id)
                    break
            time.sleep(1)

    def start(self):
        self._thread = threading.Thread(target=self._monitor, daemon=True)
        self._thread.start()

    def stop(self):
        self._stop.set()
        if self._thread:
            self._thread.join(timeout=2)
        clear_xxx_instance(self.device_id)

def initialize_xxx_connection():
    """init.py 在启动阶段调这个，按 device_config.json 批量拉起。"""
    for dev in device_config.get_device_list("xxx") or []:
        dc = DeviceConnect(dev["name"], dev["ip"], dev["port"])
        if dc.ctrl.is_connected:
            dc.start()
            _connections[dev["name"]] = dc

@atexit.register
def shutdown():
    _shutdown_event.set()
    for dc in list(_connections.values()):
        dc.stop()
```

#### 注意事项

- **解释器退出时**必须检查 `sys.is_finalizing()` 并优雅返回；否则 daemon 线程在 shutdown 阶段访问已释放对象，会打一串 Traceback。
- 下发类方法要在 `self._lock` 里做，避免多线程同时写 socket 导致粘包。
- 连接失败**不要**在 `__init__` 抛异常；实例要能以"半死"状态存在，由 service 层根据 `is_connected` 决定后续。
- 重连时**先清实例再重建**，不要尝试复用坏的 socket。

- `controllers/client/vm_client.py`（Vision Master，单连接多指令）

### 3.2 厂商 SDK / DLL 包装模板

**适用**：厂商只提供了 Python 导入包、.dll、.so、.pyd；通讯细节不可见，只能调他们给的函数。Hitbot 机械臂、海康某些相机、国产 PLC 的 OPC SDK。

#### 文件结构

```
controllers/<family>/
├── <device>.py
└── lib/<平台>/            # 厂商原生二进制
    ├── XxxInterface.pyd   # 或 .so / .dll
    └── *.dll
```

#### 骨架与坑

```python
import os, sys, time
current_dir = os.path.dirname(os.path.abspath(__file__))
lib_path = os.path.join(current_dir, "lib", "Python_64")
if lib_path not in sys.path:
    sys.path.append(lib_path)
# ❌ 不要在模块顶层 os.chdir(lib_path)
# 一旦顶层切换 cwd，Flask、APScheduler、WebSocket 里的相对路径（比如
# public/params/*.json）全部读不到，整个项目会诡异地崩。
from XxxInterface import XxxInterface

class XxxController:
    def connect(self, params):
        original_cwd = os.getcwd()
        try:
            # ✅ 仅在 DLL 加载瞬间临时切换，立刻切回
            os.chdir(lib_path)
            self._raw = XxxInterface(params["card_number"])
            self._raw.net_port_initial()
        finally:
            os.chdir(original_cwd)
        # 然后按 SDK 文档轮询 is_connect()
        start = time.time()
        while self._raw.is_connect() != 1:
            if time.time() - start > 10:
                raise TimeoutError
            time.sleep(0.1)
        self._connected = True
```

#### 注意事项

- **不要 `os.chdir` 到 lib 目录然后忘了切回**。DLL 加载只在调 `xxxInterface(...)` 那一瞬间需要当前目录里有 .dll，加载完就应该 `chdir` 回原路径。这是本项目踩过的大坑。
- 厂商 SDK 往往不是线程安全的 —— 调用前用 `self._lock`。
- **Cython 构建注意**：`build_cython.py` 在 Windows 上会把 `controllers/` 全部降级为 `.pyc`，因为 DLL/ctypes 与 Cython 编译产物冲突。新加控制器如果要 load DLL，也要遵循这个规则。

### 3.3 Modbus 设备模板（TCP / RTU，多从站复用）

**适用**：PLC、电动夹爪、四色灯塔、带 Modbus 接口的传感器。**一个物理连接（一台 PLC 或一路 RS-485）下往往挂多个从站**，必须能让上层按 `device_id` 拿到"看起来独立"的控制器。

#### 核心思想：物理连接 + 虚拟实例

```
┌─────── 业务层看到的实例 ───────┐
 controller_plc_main            (slave_id=1)
 controller_gripper_left        (slave_id=3)
 controller_lighting_tower      (slave_id=6)
       └─────┬──────┘
             │
             ▼
┌──── 实际只有一份物理连接 ────┐
 ModbusController(tcp, 192.168.1.5:502)
       or
 ModbusController(rtu, COM3)
```

包装器模式：

```python
class VirtualInstanceController:
    """
    代理所有方法到物理 ModbusController，但自动注入/替换 slave_id。
    两套策略：
    1. 支持 slave_id 参数的方法（read_*, write_*）：强制覆盖 kwargs['slave_id']
    2. 内部嵌套调用但不接受 slave_id 的方法（execute_config）：
       用锁 + 临时改 base.slave_id 再还原
    """
    def __init__(self, base_controller, device_id, slave_id):
        self._base = base_controller
        self._slave_id = slave_id
        self.device_id = device_id

    def __getattr__(self, name):
        attr = getattr(self._base, name)
        if callable(attr) and name in _MODBUS_METHODS:
            def wrapper(*a, **kw):
                with self._base._lock:
                    if name in _METHODS_WITH_SLAVE_ID:
                        kw["slave_id"] = self._slave_id
                    original = self._base.slave_id
                    self._base.slave_id = self._slave_id
                    try:
                        return attr(*a, **kw)
                    finally:
                        self._base.slave_id = original
            return wrapper
        return attr
```

上层用法统一：

```python
from controllers.modbus.modbus import get_modbus_controller
ctrl = get_modbus_controller(device_id="主PLC",   connection_type="tcp",
                             ip="192.168.1.5", port=502, slave_id=1)
gripper = get_modbus_controller(device_id="左夹爪", connection_type="rtu",
                                port="COM3", baudrate=115200, slave_id=3)
```

#### 注意事项

- **不要**把 `ModbusController` 实例缓存在 service 局部变量里过夜，因为 `_handle_communication_error` 出错后会把实例从 `_device_manager` 里踢掉，下次调用要靠 `get_modbus_controller(...)` 重建。
- 新增对外方法时，要同步更新包装器的白名单 `_is_modbus_operation` 和 `_method_accepts_slave_id`，否则虚拟实例无法正确代理。
- 读写都要走 `self._lock`，尤其 RTU 串口不能并发。

### 3.4 串口自定义协议模板

**适用**：仪器厂商给了一份"帧格式 + 指令表 + CRC 算法"PDF 的东西。典型：大肯移液器、蠕动泵、小型温控箱。

#### 骨架

```python
import serial, time

class XxxDriver:
    def __init__(self, port="COM4", baudrate=115200, timeout=1):
        self._serial = serial.Serial(
            port, baudrate,
            bytesize=8, parity="N", stopbits=1, timeout=timeout,
        )

    def close(self):
        self._serial.close()

    # ---- 指令编解码 ----
    def _build_command(self, name: str, params: list, device_id=2) -> str:
        """按厂商格式打包（头 + 地址 + 指令 + 参数 + CRC）。"""
        ...

    def _wait_for_completion(self, timeout=5.0, device_id=2) -> bool:
        """轮询状态码直到到位 / 异常 / 超时，返回 True/False。"""
        start = time.time()
        while time.time() - start < timeout:
            self._serial.write(self._build_command("d", [], device_id).encode())
            resp = self._serial.readline().decode().strip()
            # 解析 resp，遇到 "到位" → return True
            # 遇到 "异常"   → return False
            time.sleep(0.1)
        return False

    # ---- 领域方法 ----
    def get_liquid(self, volume_ul: int) -> bool:
        self._serial.write(self._build_command("n", [volume_ul]).encode())
        ack = self._serial.readline().decode().strip()
        if ">02n01" not in ack:
            return False                 # 指令下发即失败
        return self._wait_for_completion()
```

#### 注意事项

- **串口是独占资源**：同一 COM 口不能被两个实例同时占用。控制器初始化时**应支持工厂 + 池模式**，`device_id` = COM 口名。本仓库 `Pipettor` 目前是裸类没加池，每次 service 请求 `Pipettor(port="COM4")` 靠短命执行 + 最后 `close()` 避开冲突 —— 这是过渡写法，**新写的串口控制器请直接加池**。
- 每个方法通常是"下发 → 读 ACK → 轮询状态"三段。**ACK 与状态查询要分开**，不要把它们合成一个 blocking 的大函数，否则后续想加超时参数时很痛。
- CRC / 校验函数写成静态或私有方法，不要作为模块级顶层变量，避免跨设备误用。

#### 本仓库参考

- `controllers/pipettor/pipettor.py`

### 3.5 HTTP / REST 设备模板

**适用**：
- 自研嵌入式设备（ESP32 鼠标）提供 HTTP 接口；
- 第三方业务系统（LIS、LMS）提供 JSON REST API。

分两种写法：

#### A. 有状态的 HTTP 控制器（鼠标、HTTP 继电器）

需要保活、需要锁。用**单例 + 设备名映射**：

```python
class MouseController:
    _instances: Dict[str, "MouseController"] = {}   # url → instance
    _init_lock = threading.Lock()

    def __new__(cls, device_name=None, device_ip=None):
        url = cls._resolve_url(device_name, device_ip)
        with cls._init_lock:
            if url not in cls._instances:
                inst = super().__new__(cls)
                cls._instances[url] = inst
                inst._initialized = False
            return cls._instances[url]

    def __init__(self, device_name=None, device_ip=None):
        if getattr(self, "_initialized", False):
            return
        # ... 从 config 拿 base_url
        self.lock = threading.RLock()                # 短命 HTTP 也要有锁，保活不打断指令
        self._initialized = True

    def _http_request(self, endpoint, params=None):
        url = f"{self.http_base_url}{endpoint}"
        resp = requests.get(url, params=params, timeout=5)
        resp.raise_for_status()
        return {"success": True, "data": resp.text.strip()}

    def click(self, button="left"):
        with self.lock:
            return self._http_request("/click", {"button": button})
```

#### B. 无状态的 SDK 客户端（LIS、LMS）

业务侧每次请求都 new 一个实例完全可以，不用池。但要**封装 URL 前缀 + 认证 + 错误规整**：

```python
class LISSDK:
    def __init__(self, base_url=None):
        self.base_url = base_url or config.get_base_url()

    def _request(self, method, endpoint, **kwargs):
        url = f"{self.base_url}{endpoint}"
        resp = requests.request(method, url, **kwargs)
        resp.raise_for_status()
        return resp.json()

    def create_sample(self, sample_no, submit_time, test_items=None):
        res = self._request("POST", "/api/samples", json={...})
        if isinstance(res, dict) and res.get("success") is False:
            raise Exception(res.get("message", "创建样本失败"))
        return res
```

#### 注意事项

- **一律带 timeout**，HTTP 库默认没有超时，会把请求线程挂死。
- 401/403/网络错误在 SDK 层 `raise Exception`，在 service 层 `try/except` 转成 `equ_manager.failed(...)`，不要在控制器层直接吞掉。
- 带保活的（如鼠标）用 `self.lock.acquire(blocking=False)`，保活线程抢不到锁就放弃 —— 技能执行**绝对优先**。

#### 本仓库参考

- `controllers/mouse/main.py`（有状态 + 保活）
- `controllers/lis_sdk/sdk.py`、`controllers/lms_sdk/sdk.py`（无状态）

## 4. 通用编码约定

### 4.1 命名

- 子目录名：英文、全小写、下划线分隔，单数（`dobot/`、`pipettor/`，不是 `dobots`）。
- 类名：`XxxController`、`XxxDriver`、`XxxSDK`（按性质选后缀）。
- 工厂三件套：`create_xxx_instance` / `get_or_create_xxx_instance` / `clear_xxx_instance`，**不要自创名字**（`new_xxx`、`make_xxx` 一律拒绝）。
- 全局池：`xxx_manager = {}`（对应单类设备）或 `_device_manager = XxxDeviceManager()`（对应多实例管理器）。

### 4.2 日志

```python
from utils.logger import logger
# 或：
import logging; logger = logging.getLogger(__name__)
```

- `logger.info` 只记**状态变化**（连上了、断开了、重连中），不要记每次正常读写。
- `logger.warning` 用于**可恢复异常**（重试中、暂时丢包）。
- `logger.error` 用于**需要人工关注的失败**（连续失败阈值、设备硬件报错）。
- **不要 `print`**；现存代码里的 `print` 是历史债，新写的不要学。

### 4.3 参数持久化

- 只有**需要跨进程重启保留**的数据（点位、库位坐标、最后一次运行结果）才用 `equ_params.update_path(...)` 写到 `public/params/`。
- 设备的运行时状态（`is_connected`、`last_error`）用实例属性，不要持久化。
- 传感器读数、位置等"用户前端要看"的，用固定路径 `sensor/<device_id>/<field>`，让前端按约定读。

### 4.4 线程安全

- 每个控制器实例有 `self._lock = threading.RLock()`，所有会修改内部状态或操作硬件的方法都要 `with self._lock:`。
- 不要在 `__init__` 里启动后台线程；由监控文件（`<device>_connect.py`）的 `start()` 显式拉起。
- 后台线程一律 `daemon=True`，但退出时仍要 `stop_event.set()` + `join(timeout=2)` 主动收尾，避免资源没释放。
- 解释器退出时检查 `sys.is_finalizing()`。

### 4.5 异常处理

- **工厂函数**：connect 失败不抛，返回半死实例；**只有参数非法、写代码错误**才抛 `ValueError`。
- **领域方法**：返回 bool / dict，不抛；真正的硬件级异常（如 OSError）记 log + 返回失败。
- **close()** 必须幂等，可以被 atexit / 手动 / 重连 多次调用。

### 4.6 退出清理

每个家族至少暴露一个 `shutdown_xxx()` 或等价方法，由 `app.py` 或家族自己 `atexit.register(...)`：

```python
@atexit.register
def _shutdown():
    for device_id in list(xxx_manager.keys()):
        clear_xxx_instance(device_id)
```

## 6. 常见反模式（别这么写）

| 反模式 | 为什么不对 | 正确做法 |
| --- | --- | --- |
| `def main(): XxxController("192.168.x.x")` 在 service 层直接 new | 每次请求重建连接，抢端口 | `get_or_create_xxx_instance(device_id=...)` |
| 模块顶层 `os.chdir(lib_path)` | 会污染全局 cwd，其他模块读不到相对路径文件 | 仅在 `connect()` 里临时切换 + try/finally 恢复 |
| 工厂函数里 `raise ConnectionError` | 导入期崩，整个 router 线程挂 | 返回 `is_connected=False` 的实例，由上层判断 |
| `print("错误:", e)` | 不进 loguru，日志系统里搜不到 | `logger.error(f"...: {e}")` |
| 后台线程没做 `sys.is_finalizing()` 检查 | 进程退出时 daemon 线程访问已销毁对象，terminal 刷一屏 Traceback | 循环首行检查一次 |
| 控制器方法名 `send_cmd_0x03_05` | service 层无法理解，改硬件就要全改 | `read_holding_registers` / `move_absolute` |
| Modbus 新增方法后忘改 `VirtualInstanceController` 白名单 | 多从站场景下 slave_id 注入失效，读错从站的数据 | 改方法签名同时改 `_is_modbus_operation` 和 `_method_accepts_slave_id` |
| 缓存 `modbus_ctrl` 到 service 层变量，长期复用 | 通信异常后 `_device_manager` 已把它踢掉，但你还在用僵尸对象 | 每次用都 `get_modbus_controller(device_id=...)` |

## 7. 与 service 层的契约

控制器只需要保证：

1. `get_or_create_xxx_instance(device_id=...)` 返回一个对象；
2. 对象有 `is_connected`；
3. 领域方法可调用、语义清晰、带返回值或返回 bool。

剩下的（参数校验、equ_manager 状态机、并发排队、错误码）全部是 service 层的事。不要在控制器里调 `equ_manager.success(...)`，**控制器不知道它自己被哪个 manage 调用**。

具体 service 层怎么写，见 `service/服务脚本框架规范.md`。
